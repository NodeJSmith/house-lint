# Brief: Standalone LLM-Oriented Python Linter

**Date:** 2026-08-10
**Status:** explored

## Idea

Extract the portable, well-tested Python hygiene checks currently proven in Hassette into a small standalone open-source package and CLI. The package codifies Jessica's house style for reuse across her Python projects. It is publicly available, but v0.1 does not attempt to accommodate other teams' practices or promise broadly portable defaults. Its value is opinionated AST- and token-aware checks associated with recurring LLM or hurried-code failure modes, not claiming to identify whether code was generated by an LLM.

## Key Decisions Made

- The v0.1 success criterion is reusing Hassette's portable checks across Jessica's Python projects with minimal setup.
- The no-configuration default set is AI-writing cruft, lazy imports, `TYPE_CHECKING` block position, and module constant position.
- The default profile intentionally represents Jessica's house style; supporting unrelated projects' competing conventions is not a v0.1 goal.
- Exception-variable naming is an opt-in opinionated rule rather than a default.
- Spec-token detection is opt-in and configurable because Hassette's AC/FR/NFR/WP/T vocabulary is not broadly portable.
- Spec-token configuration remains specific to that rule in v0.1. The package will not become a general user-defined regex lint platform.
- Spec-token configuration prefers constrained literals/prefixes over arbitrary regexes, declares comment/docstring/filename scopes explicitly, validates and compiles configuration once at startup, and enforces documented work and finding limits. Raw regex support is not assumed; `/mine-define` must justify it against this safer default.
- File-size checking is opt-in and configurable rather than a default.
- Every rule is suppressible; no rule claims to be incapable of false positives.
- A normal suppression uses one package-wide pragma containing a rule ID and a mandatory reason.
- V0.1 needs trailing same-line and immediately preceding `ignore-next` suppressions. Whole-file and paired block suppressions are deferred until a shipped rule demonstrates the need.
- Malformed suppressions and unknown rule IDs fail. Suppressions that no longer hide a finding produce an unused-suppression diagnostic.
- Suppressions are parsed from real comment tokens and attach to Python statements, not physical lines: trailing `ignore` attaches to its containing statement and preceding `ignore-next` attaches to the next statement. A pragma suppresses all findings for its listed rule IDs whose spans belong to that statement. Disabled-rule pragmas are not unused; malformed syntax, unknown IDs, conflicting duplicate ownership, and enabled-rule pragmas that consume no finding are diagnostics. Exact precedence and multi-ID grammar remain for the design to name, not invent implicitly during implementation.
- Rule IDs and configuration receive best-effort compatibility before 1.0: changes are documented with migrations, but minor pre-1.0 releases may break them.
- If scope must be cut substantially, spec-token and file-size rules are cut before the four default checks or the unified suppression contract.
- The design covers only the standalone `llm-lint` repository. Hassette is source evidence, not an implementation target.
- The design must include a per-rule behavior matrix that marks each source behavior as preserved, deliberately generalized, or dropped. This defines the standalone semantic boundary without adding Hassette adoption, compatibility aliases, or migration work.
- The design must define the v0.1 CLI contract before implementation: finding and operational-error schemas, deterministic project-root and configuration precedence, file-discovery semantics, exit categories, stable human output, minimal machine-readable output, and scan summaries including selected root, config, rules, scanned files, and errors.

## Open Questions

- Exact package name and availability on PyPI.
- Exact rule-ID namespace and stable mapping from the candidate checks.
- Exact unified pragma spelling, punctuation, multi-ID grammar, and diagnostic severity for unused or conflicting suppressions.
- Whether suppression reasons have a minimum meaningful-content rule beyond non-whitespace text.
- Whether unused-suppression diagnostics use a normal public rule ID and whether they can themselves be suppressed.
- Whether the constrained spec-token model needs any raw-regex escape hatch beyond literals and prefixes.
- Whether separate content and filename patterns are necessary or one pattern list can declare scopes.
- Whether v0.1 includes spec tokens and file size or deliberately ships the smaller four-rule core first.
- Whether convenience commands such as `list-rules` and `explain` belong in v0.1 beyond the required `check` and machine-readable output contracts.
- Exact schemas and exit-category names for findings, configuration errors, incomplete scans, and operational failures.

## Scope Boundaries

### In

- A standalone installable Python package and CLI suitable for `uvx` or `pipx`.
- Python-aware checks using the standard library AST and tokenizer where appropriate.
- Four default checks: AI-writing cruft, lazy imports, `TYPE_CHECKING` placement, and constants placement.
- Shared rule IDs, findings, file discovery, configuration, and suppression parsing.
- Deterministic root/config/file discovery, explicit incomplete-scan behavior, human output, minimal machine-readable output, and stable exit categories.
- Required-reason same-line and immediately preceding suppressions.
- Characterization tests adapted from Hassette as behavioral evidence.
- A per-rule preserve/generalize/drop matrix with canonical standalone rule IDs and finding ownership.
- Potential opt-in configurable spec-token, file-size, and exception-name rules if they fit the agreed v0.1 scope.

### Out

- Changes to Hassette dependencies, hook configuration, CI, annotations, scripts, or tests.
- Compatibility aliases for Hassette's existing rule-specific annotation forms.
- A generic configurable regex-rule engine or plugin framework.
- Ruff, Flake8, or Pylint plugin integration.
- Claims that findings prove LLM authorship.
- TypeScript, frontend, documentation-site, release, schema, and Hassette architecture checks.
- Auto-fixing unless definition finds a narrow compelling case.

### Deferred

- PMD duplicate-code detection and its Java/tool-download requirements.
- Whole-file and paired block suppressions.
- Configurable architecture boundaries and test-factory registries.
- Markdown or general prose linting.
- SARIF, editor integrations, hosted CI actions, and broad public-support polish.

## Risks and Concerns

- The package name and framing may promise reliable LLM detection when the rules are actually opinionated hygiene policies.
- The four-rule default is intentionally opinionated. False-positive validation should cover Jessica's projects, not a representative cross-section of unrelated house styles.
- A generic pattern DSL would compete poorly with `pygrep`, Semgrep, Vale, and similar tools while increasing configuration and compatibility burden.
- Configurable pattern matching needs bounded work, finding limits, startup validation, and explicit scopes; raw regex support would expand that risk and requires separate justification.
- Mandatory suppression reasons improve auditability but require careful parsing around multiple comments and other tools' pragmas on the same line.
- Statement-based suppression ownership must remain predictable as findings move or rules change; characterization tests must cover multiline statements, multiple findings and IDs, other tools' pragmas, disabled rules, and duplicate/conflicting suppressions.
- AST parsing means syntax errors and unsupported future Python syntax must produce clear operational failures.
- Public rule IDs, pragma syntax, and config keys become compatibility surfaces even in a lightly supported package.
- Copying checks without centralizing their common source extraction and suppression behavior would reproduce Hassette's current inconsistency.

## Codebase Context

- Hassette's portable checkers are standalone standard-library scripts sharing path, AST/docstring, tokenizer, and reporting helpers in `tools/lint_helpers.py`.
- `tools/check_llm_cruft.py` scans only comments and docstrings, deliberately excluding arbitrary data strings.
- `tools/check_spec_tokens.py` separately scans comments, docstrings, and filename segments using hardcoded planning-token regexes.
- `tools/check_lazy_imports.py`, `tools/check_type_checking_position.py`, and `tools/check_constants_position.py` provide portable AST-based structural checks.
- Existing annotations are inconsistent: `lazy-import`, `constant-after-def`, `file-size-exempt`, `factory-local`, `coordinator-internal`, and paired/file-level duplicate-code markers.
- Actual Hassette usage confirms that default portable rules need both trailing and immediately preceding suppression placement. File and block scopes are currently driven by file-size and duplicate-code checks, not the four-rule core.
- Prior-art research found no small existing package that combines exact Python comment/docstring extraction, filename matching, configurable project vocabulary, and a unified suppression model. Raw regex needs are already served by pre-commit `pygrep` and ripgrep; Semgrep and Vale are heavier alternative ecosystems; Ruff does not support third-party custom rules.
- The target repository was empty and was initialized as a Git repository during this grill. `cfl spec init` still rejected the unborn repository because it has no initial commit, so this feature directory was created directly.
